# Historical observations validation

## Measurement semantics

An **observation** is factual evidence received or decoded at a recorded
time: for example a discovery receipt, an ENR, an authenticated Hello, an API
response, or a probe outcome. A **measurement attempt** is an operation that
tried a stated endpoint/protocol stage. It remains an occurrence even if the
same state was observed earlier. A **successful evidence record** means that
the named exchange completed, within that stage's rules; a successful TCP
connection alone says nothing about Auth, Hello, or Status. `NOT_TESTED` means
the stage was not executed because it was outside the operation or a
prerequisite did not complete. `NOT_OBSERVED` is not a persisted stage state;
absence of a record is not a negative measurement.

Cryptographic node ID is the canonical identity. Discovery endpoints keep
address, family, UDP/TCP purpose, source and provenance independently. Same
identity/multiple endpoints and different identities/same endpoint remain
representable. A run row is a completed inspection operation. Every repeated
run has its own ID and time; identical normalized evidence may share a payload
hash. Discovery `observed_at`, run start/completion, per-attempt timestamps,
and enrichment `looked_up_at` describe different events. They are not treated
as simultaneous. The latest inspection order is start time descending, then
run ID descending; the normal node dashboard uses the existing endpoint
projection and its canonical identity preference. Missing legacy times do not
become 1970 timestamps or invented runs.

This is a single-observer sample, not a census. Bootstrap choices, discovery
sampling, observer routing/firewalls, candidate port selection, public peer
responses and local IPv6 connectivity can all affect what is seen. An
observer restriction, a local network limit, a protocol outcome, and a peer
outcome are separate interpretations. These data do not establish that a
nonresponding peer is faulty, that an endpoint disappeared, that a service is
absent elsewhere, that an ASN proves hosting, or that an MMDB update means a
node moved. Current single-observer measurements are **not automatically
representative of the Ethereum network**. Population claims would need an
explicit sampling method and denominator; future Network Analytics owns that
work.

## Deterministic validation

`mvn test` and `mvn package` each passed **119 tests, zero failures, zero
errors, zero skips** on the final Java sources. New tests cover:

- repeated occurrence semantics on small fixtures, payload
  deduplication, client/capability succession, later Hello failure, and
  preservation of earlier authenticated facts;
- endpoint and IPv4/IPv6 coexistence, two identities on one address, and
  source/time-preserving endpoint indexing;
- equal timestamp tie order, bounded pagination, latest projection, separate
  RPC/Beacon evidence, and the history HTTP response matching repository data;
- dataset version/lookup-time association, Clear All Data including dependent
  rows, reinsertion after clear, and foreign key integrity;
- a blocked stale history completion using latches, clear and shutdown
  generation barriers, fresh-generation restart, and no late run insertion;
- transaction rollback when the latest projection write fails, version 4
  migration rollback under an injected trigger, representative legacy upgrade,
  and no backfill from missing legacy time.

Existing ENR tests cover sequence succession, invalid signatures and trusted
endpoint exclusion; existing protocol tests cover downstream `NOT_TESTED`,
RLPx/Hello/Status evidence and RPC/Beacon independence. No Change Detection
event is generated by these tests.

The history query endpoint returns at most 50 rows per request; the repository
limit is 100. The normal node CSV header and columns remain unchanged. The
JSP syntax check and renderer check passed. The history UI presents successive
factual runs, timestamps, endpoints, stage outcomes and expandable details;
it does not label transitions.

## Performance and storage growth

The deterministic benchmark utility refused to open an existing path. On a
fresh temporary SQLite database it wrote 1,000 identical factual payloads
at 1,000 distinct run times. It verified from SQL that `inspection_runs`
contained 1,000 rows, `COUNT(DISTINCT evidence_hash)` was 1, and
`inspection_evidence` contained exactly 1 row. The first bounded 20-row page
was ordered `0999` through `0980`; the next page began `0979`.

| Measurement | Observed |
| --- | ---: |
| Database after schema + one latest node | 151,552 bytes |
| Database after 1,000 occurrences | 999,424 bytes |
| Growth | 847,872 bytes |
| 1,000 transaction writes | 439 ms |
| Bounded 20-row identity query | 2,489 µs |
| Latest projection query, 1 row | 12,599 µs |
| Process heap used before / after | 20,544,376 / 61,274,776 bytes |

Heap figures include JVM class loading and allocation, not a steady-state
memory leak measurement. SQLite's query plan used
`idx_inspection_identity_time` and the payload hash index for the bounded
query. The repository SQL uses `LIMIT`; it does not materialize all 1,000
occurrences for a 20-row page. History introduced zero workers and zero
queues; it writes synchronously in existing scanner/inspection work.
Automatic destructive retention is absent, so operators must plan for
long-term occurrence and discovery/ENR growth. Both temporary benchmark
databases were removed after measurement; the live database was untouched.
