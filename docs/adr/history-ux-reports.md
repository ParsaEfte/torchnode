# History UX and reports

## Read-only baseline audit (2026-10-01)

At `78fd187`, Dashboard v2 links each latest projection to `/node?key=…` and to Network Analytics. Opening `/node` starts a new inspection. The page emphasizes that active inspection's latest values, diagnostics, and short live timeline. Separate lists show completed inspection runs and derived changes, each 20 at a time with cursor pagination. Runs retain distinct IDs even when evidence payloads are shared. The page has no discovery or ENR occurrence history despite bounded repository readers for both. Endpoint and enrichment context are primarily latest views. The live timeline's name risks implying comprehensive history. Change rows give source IDs and values but no direct source navigation. A single dense two-column grid puts raw context and summary cards at similar weight. Mobile layouts collapse cards, but long history summaries and endpoint strings need explicit wrapping. JS uses `textContent` for remote evidence; static skeleton markup uses `innerHTML`. The analytics page already exposes scoped metrics, denominators, unknown counts, and a 250,000-row safety cap. It lacks a print-oriented human report. CSV is a latest-projection export and carries observation JSON; it is outside this milestone.

The existing query clocks are `observed_at` for discovery/ENR, `started_at` for runs, and `current_observed_at` for changes. Run history allows null start time. Cursor queries use timestamp plus ID for deterministic ties. Latest projection rows are distinct from durable occurrences. No evidence supports interpreting gaps as disappearance or repeated receipts as continuous presence.

## Design rules

History presents domain-specific bounded lists with source, timestamp, endpoint context, and expandable raw details. Discovery grouping is presentation only: compatible source, provenance, and exact ordered endpoint payload (address, family, transport, purpose, port) within one fetched page; the displayed count is an occurrence count in that page. Grouped observations remain expandable individually. The cross-domain overview also groups exact compatible ENR payloads or address/dataset/enrichment payloads, with each clock exposed on expansion. Groups do not assert continuous presence across first and last timestamps. Runs never group by payload hash. Untimed runs carry an explicit unknown chronology label. Equal timestamps are displayed as ties, without causal claims. Derived changes stay separate and show their source IDs and comparison rule version.

The overview is a bounded preview of the first 20 rows per domain, not a complete global top-N chronology. It sorts by normalized UTC domain clocks and places untimed runs last. Discovery/ENR/run cursors use normalized fractional timestamps plus stable row IDs. The enrichment reader joins distinct observed addresses to historical address/dataset lookup occurrences in one bounded query, without assigning lookup results to an identity as intrinsic location. Every domain has a separate Load more control. No presentation grouping deletes an occurrence or writes aggregate state.

The active inspection remains a separate latest measurement. Its P2P pipeline distinguishes PASS, FAILED, and NOT_TESTED; independent RPC and Beacon candidate outcomes remain outside that pipeline. ENR entries show structural validity, signature, identity comparison, sequence, endpoint claims, and raw record details. Trusted labeling follows the existing `EnrEvidence.usable()` rule. A sequence advancement is a comparison of observed records and does not imply intermediate records were seen. Changes are derived evidence and are not a second raw observation stream. Endpoint claims retain source and purpose. Client conflict and unknown-version semantics remain in the existing run and analytics views.

The report is a live view of `NetworkAnalytics.Report`, with the same validated scope and safety limit. It stores no report state. Each metric keeps its counting unit, denominator, unknown count, rule, and overlapping-bucket semantics. Print CSS renders on white, hides navigation and controls, and retains scope and methodology. Reports describe TorchNode's observer vantage, not the Ethereum population.

The implementation uses the existing JSP/servlet architecture and DOM text nodes for remote evidence. Query parameters accept explicit window bounds or all-available mode; malformed, contradictory, oversized, and unsupported scopes fail. History pages are capped at 50 requested rows, with 20 as the UI page size. The report request computes Network Analytics once. No extra cache survives Clear; history loaders discard results after the inspection status reports a deleted generation. The existing generation barrier and Clear transaction remain responsible for scanner lifecycle safety. CSS adds semantic headings, native `details` disclosure, visible keyboard focus, mobile wrapping, reduced-motion respect from the current inspection page, and white print styling. No new schema objects or indexes are needed.

No schema or analytics semantic change is intended. Migration 6, new durable report truth, public API contracts, bulk exports, and server-side PDF generation are outside this milestone.
